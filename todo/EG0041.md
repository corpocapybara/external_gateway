Follow-up from EG0023 (merged a01c87e, 2026-11-14).

Problem: `a.b: {}` (an empty map body) unmarshals to a non-nil `*Operation` with no connector. The EG0023 nil guard in loadFromFile (internal/policy/registry.go) does not catch it, and neither does anything else in the op loop. More generally, an op whose connector is empty or unknown (e.g. a typo `http_rest`) loads, and when called it matches no branch of the dispatch chain in internal/server/server.go (~568-585). It falls through with no error, an empty body and status 0, and is audited as allow (.ai/CONNECTORS.md:42-44 documents this). Also, loadFromFile ranges over the `cfg.Operations` map and returns on the first bad op, so a file with several bad ops names a different op from run to run.

Owner decisions (2026-11-14, refinement Q&A):
- Refuse any unknown connector at load, not only an empty one. No runtime `else` in the dispatch chain.
- The 3 `form-session` CodiMD ops in config.example/operations.yaml are to work, not be removed: form-session gets wired into dispatch in EG0042, which blocks this todo.
- Keep todo ids in code comments (39 in Go code already). The draft's "drop EG0023 ids from comments" item is dropped.
- Check ops in sorted id order and return the first error (not all errors joined).
- One change, not split.

Checked 2026-11-14: the local ops files (operations.cc/cm/thp.yaml) use only email, http-rest, local-service, mcp, postgres and jira-worklog, so the stricter check does not stop a deployed service. config.example/operations.globex.yaml uses email, http-rest, local-service and postgres. Callers of NewRegistry: cmd/egw/main.go (startup), server.go reload handler, cmd/egw-desktop/configedit.go (validation).
