Follow-up from EG0023 (merged a01c87e, 2026-11-14): the review notes and `todo done` output left three loose ends in the loading of the ops YAML. Refinement decides if they stay one change or split.

1. `a.b: {}` (an empty map body) unmarshals to a non-nil `*Operation` with no connector, site, method or path. The EG0023 nil guard in `loadFromFile` (internal/policy/registry.go) does not catch it, and nothing else in the loop does: the op loads, is registered, and only fails (or misbehaves) when called. Proposed: refuse an op with no connector at load time, naming the op, with a test in internal/policy and, possibly, a reload test like TestReloadRefusesNilOperation.
2. Cleanup: three code comments still name the done todo EG0023 (`todo done` reported them): internal/policy/nil_operation_test.go:11, internal/policy/registry.go:321, internal/server/admin_hardening_test.go:245. Reword them to describe the behaviour without the todo id (or keep them, if the project prefers ids in comments: owner question).
3. Error naming: `loadFromFile` ranges over the `cfg.Operations` map and returns on the first bad op, so a file with several bad ops names a different op from run to run. Proposed: iterate the op ids in sorted order so the error is deterministic (or collect every bad op into one error). Also uncovered by tests: `a.b: null` / `a.b: ~` and a nil op next to valid ops (the guard handles both today).
