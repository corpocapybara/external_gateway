**`jenkins.build_with_params` passes only `PUBLISH`, so a parameterized test job can't be started with chosen image tags** (2026-11-04). thp's develop regression `job/AutomatedTests/job/Regression/job/Automated.Tests.Regressions/job/develop` takes 23 Active Choices `*ContainerImageTag` params (automated-tests `src/Thunderpick.ApiTests/.jenkins/JenkinsfileRegression`, stage `Set versions`). Its for (2026-11-04, via /feedback).

Refinement findings (2026-11-12): the trailing "Its for" sentence was already truncated in the original TODO.md line (commit 7e2187d); feedback.log has no build_with_params entry, so it cannot be recovered. The op is in the gitignored operations.thp.yaml:1949-1965: params env, job, PUBLISH (enum pinned to "false"), no body template, so PUBLISH goes out as a query param; granted at config.thp.yaml:104 and :185; documented at .ai/OPERATIONS.md:440. A generic params map is impossible today: undeclared params are refused (registry.go:566) and there is no map-to-query feature. The 23 *ContainerImageTag names live in thp's automated-tests JenkinsfileRegression, outside this repo.
Owner questions: (1) approach: (a) declare the 23 tag params in YAML, each with a tag pattern (ops-only, fully constrained, a YAML edit per new tag) or (b) a generic params map with an allowlist/regex (new server code, cross-bucket, risk high)? (2) what was the stated need: only the develop regression job, or any parameterized job? (3) must PUBLISH stay pinned to false?

Owner answers (2026-11-12): declare the *ContainerImageTag params in YAML (no generic params map); scope is the develop regression job; PUBLISH stays pinned to false. The param names are read from thp automated-tests src/Thunderpick.ApiTests/.jenkins/JenkinsfileRegression, stage Set versions (outside this repo). The op lives in the gitignored operations.thp.yaml, so the only tracked change is the .ai/OPERATIONS.md row.

Refinement round 1 (2026-11-12): jenkins.build's allow_fields (operations.thp.yaml:1840) drop actions[].parameters, so the build's parameters cannot be read back through egw; the check is the build start plus one recorded observation in Jenkins (stage Set versions output or the build's Parameters page). All op edits are in the gitignored operations.thp.yaml, so items 1-3 are deploy steps checked by live calls; the tracked change is the .ai/OPERATIONS.md row. Tag pattern follows the Docker tag grammar. Optional params without a default are absent from the params map (ApplyDefaults only fills declared defaults), so an omitted tag is not sent and Jenkins keeps the job's own default.
