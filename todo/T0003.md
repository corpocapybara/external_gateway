**`jira.search` returns a fixed field set; callers can't ask for `fields`** (2026-11-04). The params are only
`jql, maxResults, nextPageToken, env`. Session 5e46f9cf (thp, 10-16) got
`{"detail":"unknown parameter: fields","rule":"validation"}`, and the docs send stripped fields (Release Notes
`customfield_10333`, components) to browser `POST /rest/api/3/search/jql` (40 fetches). Add an allowlisted
`fields` param and keep response shaping.

Checked against the code (2026-11-11):
- `type: list` params get no validation at all: `ValidateParams` (`internal/policy/registry.go:349`) has no
  `list` case, and `CheckConstraints` (`registry.go:477`) silently skips unknown constraint types.
- `buildBody` (`internal/server/server.go:1502`) renders a list param as JSON (`formatParamValue`, `server.go:1572`),
  so `"fields":{{fields}}` in a body template yields a JSON array; values cannot break out of it.
- Constraints run before `ApplyDefaults` (`server.go:454-467`, `529-549`), so an absent `fields` is never checked and
  its op default is what goes upstream.
- The live ops files (`operations.<ws>.yaml`) are gitignored; thp's `jira.search` (`operations.thp.yaml:81`) sends
  13 fixed fields.

Owner answers (2026-11-11, refinement):
- Jira-specific check only, not a generic `values:` allowlist on `type: list`.
- Live change for thp only; allowlist = today's 13 fields + `components` + `customfield_10333`; default stays
  today's 13.
- The owner runs `deploy/update.ps1` after the merge; the live deploy is not part of acceptance.
