Found in EG0039 review (finding B1, rejected there per design D6/D9 and frozen acceptance). Today every rejected call refreshes once, so a dead or revoked refresh token hits the token endpoint on every call.

Checked 2026-11-16: email `withEmail` (internal/server/email_auth.go) refreshes and retries once on ErrAuthRejected; the http-rest path (internal/server/server.go, the 401 branch after the upstream call) refreshes and retries once on a bearer 401. Both call `refreshOAuthToken` under `oauthRefreshMu`, with no cooldown or negative cache. The admin handlers already reset in-memory caches (`s.creds.clear()`, `s.formSessions.Clear()`) on /admin/secrets set/delete and /admin/reload; the cooldown reset goes beside them. `credCache.now` (internal/server/credential_status.go) is the existing injectable-clock pattern.

EG0045 (done) changed the same function (the used-token argument and the under-lock check). A refresh that EG0045 skips is not a still-rejected refresh.

Trade-off: a cooldown hides a fix made outside the admin paths (e.g. a manual credential-store write) until the window ends; note it in docs/HOTMAIL.md.

Owner answers 2026-11-16: refinement "review till green" (one more verifier round after round 3, and on until a round passes); the window is a config field (`oauth.refresh_cooldown`), not a package constant, so the todo needs a written design (public config change).
