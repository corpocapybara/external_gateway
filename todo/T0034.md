Found while working on T0029 (2026-11-12). A local egw.exe, run as the user (not LocalSystem) with config.thp.yaml on port 18544, crashed on GET /capabilities?workspace=thp: nil pointer dereference at internal/secrets/wincred_store.go:18 (creds.CredentialBlob), reached via internal/server/credential_status.go checkCredential. The code checks err but not creds == nil. The deployed LocalSystem services did not crash, because their secrets exist.

Checked at refinement (2026-11-12) against the installed github.com/danieljoos/wincred v1.1.2 (go.mod):
- GetGenericCredential (wincred.go:23-29) returns (nil, nil) only when sysCredRead (sys.go:67-81) sees a nonzero CredReadW return with a NULL credential pointer (sysToCredential returns nil for nil, conversion.go:48-51). When CredReadW fails, the error from Proc.Call is always non-nil, so Resolve's existing err check catches it.
- So the crash means CredReadW reported success without a credential; why it did is unknown. Not reproduced: a probe run as the user on 2026-11-12 read egw/thp/gitlab and egw/thp/jira with a non-nil credential and a nil error.
- The panic killed the whole process because checkCredential runs in a goroutine (`go func(i, t, gen)` in credential_status.go), outside net/http's per-handler recover.
- WinCredStore.LastWritten (`len(cred.CredentialBlob)`) and WinCredStore.Delete (`cred.Delete()`) in the same file have the same unchecked nil; they are fixed in this change too (same class).

Out of scope: a recover in the /capabilities credential-check goroutine (a separate hardening, not asked here).
