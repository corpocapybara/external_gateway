No code reads constraint type kibana_index_scope (CheckConstraints in internal/policy/registry.go handles only jql_scope, jira_fields, readonly, allowed_tables). cm's kibana.search (operations.cm.yaml ~980) takes a free-string index param (default logstash-*) used in its path, and config.cm.yaml sets kibana_indices [logstash-nth-stg*, logstash-*], so an agent can search any index. The thp kibana.search also has a free-string index. Unverified side observation: the path uses double-brace {{index}} while pathPlaceholder (internal/server/pathtemplate.go:12) matches single braces, so the outer braces may stay in the path. Owner 2026-11-11: P2, own todo. Proposed acceptance: kibana_index_scope refuses an index not matching a workspace kibana_indices glob (comma lists and wildcards handled), with policy and server tests.

Refinement findings (2026-11-12): kibana_index_scope is registered as constraintNoEffect (internal/policy/constraint_types.go:35-36) and has no CheckConstraints case (registry.go:650-678). Declared in operations.cm.yaml:1010 and config.example/operations.globex.yaml:480 with indices: $workspace.kibana_indices; not declared on the thp kibana.search. KibanaIndices is a workspace policy field (internal/config/config.go:155). The double-brace path is real and split off as T0031. Live ops/config files are gitignored: tracked deliverable is policy/server code + config.example + tests; declaring the constraint on live ops is a deploy step.
Proposed acceptance (pending owner answers): kibana_index_scope becomes checked; the index param is split on commas and each element must match a kibana_indices glob, else 403 naming the constraint; policy tests TestKibanaIndexScope* (allowed, refused, comma list with one bad element, omitted index using the op default); a server test shows a refused index gets 403 with no upstream call.
Owner questions: (1) an agent pattern wider than allowed (* or logstash-* when only logstash-nth-stg* is allowed): refuse (pattern must be a subset) or allow (pattern matches at least one allowed glob)? (2) cm config lists both logstash-nth-stg* and logstash-*: is logstash-* intended (it makes the first redundant)? (3) empty kibana_indices: refuse all or allow all (pg precedent allows all, connector.go:40)? (4) refuse - exclusion patterns and _all? case-sensitive? (5) check the op's default index too? (6) live ops declaration: deploy step here or a separate todo?

Owner answers (2026-11-12): a requested pattern wider than allowed is refused (each requested pattern must be covered by an allowed glob); an empty kibana_indices leaves the op unscoped, as pg_allowed_tables does; _all and -exclusion patterns are refused; matching is case-sensitive; the live ops declaration is a deploy step in this todo; cm keeps its logstash-* entry. The covers-check (pattern within glob) is the new rule to design. T0031 (double-brace path) interacts with the end-to-end check.

Refinement round 1 (2026-11-12): CheckConstraints runs before ApplyDefaults (server.go:462 vs 470, and 537 vs 552), so the constraint must read the op's declared index default itself. A constraint refusal is writeDeny with rule "constraint" and the error in detail (server.go:462-464). The existing glob helper (server.go ~2557) lowercases and uses filepath.Match, so it cannot be reused. Covers semantics: only * is a wildcard (Elasticsearch index patterns); the design step fixes the algorithm and the full case table; it may be conservative (refuse what it cannot prove covered) but never allows an uncovered pattern. Element parsing (trim, empty elements refused) is a fail-closed refinement choice. The deploy refusal happens before any upstream call, so it does not depend on T0031.

Refinement round 2 note (2026-11-12): config.thp.yaml sets no kibana_indices (config.cm.yaml does), so by the owner's empty-list answer thp stays unscoped after this todo; declaring the constraint there only takes effect once the owner sets thp kibana_indices. cm lists logstash-*, so cm's default index logstash-* stays allowed.
