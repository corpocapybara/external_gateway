Found in EG0040's live run (2026-11-14): hotmail.list_mailboxes returned mailboxes[].attrs and hotmail.read returned cc and seq although the ops' allow_fields list only mailboxes[].name and uid/subject/from/to/date/body/flags.

Checked 2026-11-16: only executeHttpConnector (http-rest and form-session) calls shapeResponse (internal/server/server.go). executeEmailConnector ends with `json.Marshal(result)` and returns 200 without reading op.Response, so every email op (hotmail.*, gmail.*) ignores allow_fields. Nothing in .ai/OPERATIONS.md or the code marks this as intended (OPERATIONS.md says allow_fields restricts the returned fields, with no per-connector exception; slack_file_content and jira_attachment_content refuse allow_fields at load, which is a different case).

Scope: email only (this todo). local-service, postgres and jira-worklog have the same gap but need an audit first (the example wireguard allow_fields do not match the connector's output, so naive shaping would strip fields): split off as a separate draft.

Behaviour change: agents stop getting fields their op does not declare (e.g. cc and seq from hotmail.read). That enforces the declared contract.
