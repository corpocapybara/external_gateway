Found in EG0039 review. Two concurrent rejected requests may each refresh today (accepted in EG0039: Microsoft does not revoke a used refresh token; recorded in docs/HOTMAIL.md).

Checked 2026-11-16: `refreshOAuthToken` (internal/server/server.go) holds `oauthRefreshMu` for the whole refresh but never compares tokens; neither the email path (`withEmail`, internal/server/email_auth.go, whose closure resolves the secret and does not return it) nor the http-rest 401 path passes the token the rejected call used. A refresh writes the new token with `resolver.Set` and calls `FlushCache()`, and `Set` forgets the cached key (internal/secrets/resolver.go), so a read under the lock after another goroutine's refresh sees the new token despite the 30 s cache. Read it with the same resolver call the paths use, not the store directly.

Change is in internal/server only (internal/secrets is read, not changed). Goes before EG0044, which builds on the same function.
