Found 2026-11-20 while delivering EG0059 (history test speed-up).

`runHistory` (cmd/tools/leakcheck/history.go) runs `git ls-tree -r -z --full-tree <tree>` once per distinct tree of
the listed commits. This repo had 737 commits and 710 distinct trees at the time, so a full `leakcheck history`
scan starts about 710 git processes. At the roughly 80 ms per git process measured on this machine, that is about a
minute. It also makes two `for-each-ref` calls (tags, then all refs) that could be one.

Proposed approach (to be settled in refinement): read tree objects through the existing `git cat-file --batch`
process (or a second one) and walk them recursively, and fold the two `for-each-ref` calls into one. Keep
gitlinks skipped and blob attribution (first commit and path that listed the blob) as today.
